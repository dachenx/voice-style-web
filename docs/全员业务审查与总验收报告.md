## 2026-10-15 发现的三个问题与最小修复方案

### 问题 1 文案写入后项目列表与详情未同步

产品、质疑、架构一致认定为明确集成缺陷，总验收核对同意。后台保存和首次确认会更新项目时间，文案面板只更新自身，没有通知项目列表与详情读取新值。用户可能看到旧时间和旧排序。

架构临时 API 实测：先建 A、后建 B，列表为 B/A；保存 A 文案后服务端变为 A/B。前端缺少对应刷新通知来自代码核对，尚未运行这一具体场景的浏览器复现。依据：[后台文案写入](../backend/app/text_documents.py)、[文案面板](../frontend/src/TextPanel.tsx)、[项目与面板接入](../frontend/src/App.tsx)。问题记录 E044。

**建议方案：**成功保存或确认文案后通知 App，复用现有写入版本保护，刷新列表及详情。需验证 A/B 排序、首次确认更新时间，以及较早响应不能覆盖新状态。它不改变业务规则，但按用户本轮要求，仍随修复包交用户决定后实施。

### 问题 2 固定保存提示范围不清

项目详情固定显示“已保存，刷新或重启后可继续”，但页面可能同时存在未保存文案。产品认为容易误导；质疑认为属于非阻断歧义，因为文案面板另有未保存提示。总验收归类为界面体验问题，**不是实际保存失败或已保存稿丢失**。

**建议方案：**限定为“项目信息已保存”，文案继续独立显示未保存、已保存、已确认状态。验证未保存文案时两种提示含义不矛盾。依据：[项目详情提示](../frontend/src/App.tsx)。

### 问题 3 新确认后已打开的历史列表未更新

先查看历史，再确认新版，文档状态会更新，已经打开的历史列表仍保留旧内容。再次点击查看历史能取得新记录；没有快照丢失的证据。质疑提出，总验收独立静态核对确认。

**建议方案：**若历史列表已经打开，确认成功后刷新列表；列表刷新失败时单独提示，不能把已完成的确认误报为失败。验证新版可见、迟到旧列表不覆盖新版、刷新失败不影响已保存快照。依据：[文案操作与历史读取](../frontend/src/TextPanel.tsx)。

## 需要明确的现行策略和未来条件

**当前参考的多窗口选择。** 当前接口没有期望版本，最后成功写入生效，其他窗口可能显示旧选择。这与文案的版本冲突检测不同，但不自动构成串项目或素材损坏。是否保持现状或增加冲突检查，见决策 B。依据：[参考激活](../backend/app/references.py)。

**文案冲突恢复。** 当前保留本地输入，用户可取消重新载入，或先复制要保留的内容再接受服务器版本。自动合并、草稿导出属于可选增强，不强加为本轮阻断。

**转换不确定项的生命周期。** 普通保存会清空 `conversion_warnings`，只改语体或通过 API 原样保存也会清空。语音角色提出、总验收代码核对确认，现有测试明确断言该行为。当前无真实转换器，不能称为真实误转事故；接真实转换组件前须决定保留至明确处理、标为过时或其他生命周期。语音建议保留并标明处理状态，“保存”不自动等于“不确定项已解决”。依据：[普通保存与转换回写](../backend/app/text_documents.py)、[现有转换测试](../backend/tests/test_text_documents.py)。本轮不擅自实施。

**试听格式与模型输入。** 24 kHz 单声道是当前试听及裁剪规格，不代表所有模型的参考要求；原件和范围保留，可供未来重新预处理。

**读音备注与其他语言。** 当前保存读音备注，并不执行发音处理。业务校验与界面仍固定普通话到武汉话，其他语言需同时扩展校验、界面、能力及测试，不能仅注册一个转换器就宣称支持。

**未来任务输入。** 任务入队应在同一操作中核对期望文案版本和所选参考，固定不可变输入；不能先检查，再过一段时间按可变当前指针生成。这是后续既定约束，不是启动 M04 的授权。

**不新增首次原稿锁定。** 当前原稿可编辑、确认快照不可变符合 D013。首次输入永久存档和全部未确认修订历史没有现行要求，不列缺陷，也不要求本轮额外决定。
