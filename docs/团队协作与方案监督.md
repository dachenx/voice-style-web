# 团队协作与方案监督员

| 角色 | 唯一任务名 | 职责 |
| --- | --- | --- |
| 主持/集成 | root | 调度、记录、展示实际意见，实施已授权事项并核验提交状态；不代替职能或总验收签署 |
| 产品 | product | 流程、文案确认、可用性和验收例子 |
| 语音技术 | speech | 方言、音色与风格验证，模型适配及实测 |
| 架构/开发 | architecture | 接口、存储、队列、恢复和版本实现 |
| 质疑/质量 | critic | 错误路径、边界、长文、退化检查 |
| 总验收代理 | chief_acceptance | 独立汇总所有成员想法，核对职能间交接和整条业务流程；发现问题给方案、影响与推荐交用户决定；无问题给逐环节报告 |
| 方案监督员 Plan Guardian | process_guardian | 逐批跟进实际代码产出，对照已批准方案、范围及验收要求检查落实，同时核对真实参与/记录；不替代各职能判断或总验收 |

按 D015，一个职能只有一个固定负责人，表中任务名是后续唯一调度名称，不表示所有代理始终在线。保留 speech、architecture，停用 speech_review、architecture_review；旧 plan_guardian 名称也不再另行调度，监督职能统一为 process_guardian。其他历史后缀同样不得作为并列岗位重新启用。

开工先查询现有代理，复用对应固定角色；无可用实例时才能用同一固定任务名恢复。若旧实例仍占用职能，应先停止其任务并完成交接，不能再加 review、v2 等同职责副本；并发名额不足时排队执行。历史审查保留原实际署名，不把已停用副本的发言改写成固定代理当时已执行。当前代理列表已无 speech_review、architecture_review，本次是取消后续角色绑定，不声称删除宿主保存的历史会话。

## 唯一执行方与证据复用（D024）

最新 D029：开发期提交及 Stop 不自动运行完整检查，按实际改动做必要定向验证并真实记录；审查复用相关证据，不为小改动反复启动全套。完整验收保留供需要时单独执行，D028 的仅本地提交安排继续有效。

同一仓库由一个主实现聊天负责写入、模型实验和完整检查；讨论聊天及审查代理只读。交接先核对其他聊天状态与实际角色实例；当前树列表及主聊天空闲不能证明跨树代理已停止。跨树不可见时须取得原负责人列明固定角色状态及待办的交接摘要，才能恢复其常驻职责，不能猜测其不存在。用户授权本聊天单独落实治理时，可使用注明身份边界的临时只读治理审查，但不得替代或新增原固定岗位。确认原负责人停止写入，移交基线、差异及待办；不能仅凭显示名称判断固定代理是否参与。各职能提交署名、已审基线、实际证据及未执行项，主持不得代签。

开发中按影响调度相关职能和固定监督员，模块完成仍收齐四职能、独立总验收及最终监督。共享冻结基线的测试日志，无须各自重复全套；完整检查期间所有参与方停止候选文件编辑，禁止多个聊天并行运行共享端口和输出目录的测试。自动强制门禁保持。

监督员按 D024 核对风险分级、单一写入/检查执行方、证据基线、错误记录轻重及重复问题升级、实验变量与停止条件；一次性轻微工具或格式失误可简记，重大、重复及门禁问题须详细 E。原有逐批方案监督、模块全员本职和独立总验收不减免。

## 职能审查与总验收

按 D020，全员本职审查的必经节点是每个模块实现完成后、正式交付前。下文“阶段完成”收齐全员意见按此模块节点执行，不扩大为每个小环节全员重复审查；开工讨论、开发中逐批方案监督及受影响职能复验继续保留。

所有固定成员分别负责：product 审业务流程与界面，speech 审语音能力与声音证据边界，architecture 审数据、接口与运行结构，critic 审异常路径及验证充分性；chief_acceptance 收齐四职能意见后独立核对交接与整体结论，process_guardian 审方案和参与落实，root 核对集成、记录及交付证据。主持与其他角色均不得代签。

报告逐一列出本模块各角色的已审范围、基线、实际证据、结论、问题和限制。不涉及的职能必须由本人解释原因，未审不得默认为通过，写了代码不等于已提交本职审查。区分“实现完成、待审查”“审查待处理”“业务及监督审查通过”和“严格本地检查及本地提交已核实、模块本地交付”；按 D028 初版完成前暂停推送、PR 与远端 CI，发布时再另核远端交付。修正后复验受影响内容，不要求无关成员重复运行同一套测试。

按 D014，每个子代理只对自己的职能负责。产品检查用户操作和业务含义；语音检查参考、语言、发音、音色及能力边界；架构检查数据、接口、版本与恢复；质疑/质量检查异常路径和验证是否充分。一个代理承担了开发任务，不等于已经提交独立业务意见；不得仅改角色署名冒充多方参与。

开工按风险和影响调度相关职能与监督员；模块完成时，由主持收齐四份实际本职意见再交独立总验收代理。提交前复核受影响职能、全员意见的有效基线及总验收结论，不要求未受影响成员重复同一审查。总验收按“用户动作 → 系统响应 → 持久数据 → 失败恢复 → 下一步”检查每个环节，区分明确缺陷、当前业务策略、体验建议和未来接入条件。有疑点只交对应职能补证，意见冲突保留原观点和总验收裁定依据，不能由主持宣布默认一致。

角色结论至少包含：本职范围、基线、事实与证据、问题或未发现问题、解决选项及限制。未运行测试明确说明；静态判断、历史测试、本轮实测和真实声音验收分别表述。无关职能写明不适用的具体理由，不能留空或复用历史 PASS。

总验收输出三种状态：`无待决问题`、`待用户决策`、`证据不足`。有问题时提供可比较方案与影响，用户选择后才实施；不得自动采取推荐方案。无问题时生成报告说明每个环节、各角色结论和通过依据。只有审查完成而问题待定时，报告必须保留待定状态，不能称为全员业务验收通过。

Plan Guardian 检查上述流程是否落实、结论是否忠于用户决定和实际证据。它不能单独替代全员与总验收。当前脚本仅检查独立监督记录的结构与内容摘要，并不能自动证明每个角色真实发言；真实参与与逐环节报告仍须由主持落实、监督员核对，不能把现有 CI 绿色当作全员业务签署。

本轮 M01–M03 补审发生在原技术交付之后。原审核 JSON 保留；新增记录只说明本轮补审，不回填成当时已经完成。当前报告见 [全员业务审查与总验收报告](全员业务审查与总验收报告.md)。

讨论聊天已建立真实 Plan Guardian 角色，后续按 D015 复用唯一 process_guardian；已有实现聊天中的固定监督员可用时，不在讨论聊天另建并列实例。代理生命周期由宿主管理，新会话须先核对已有实例。开工、阶段完成、提交前是必触发节点，开发中的逐批代码监督按 D018 执行。持续跟进由实际代码产出触发，不宣称代理永久后台在线，也不把定时空转当作监督。监督员只读，不与开发者同时改文件。

## 开发中的逐批方案监督

按 D018，每完成一批可复核的实现、修复或测试改动，主持主动提交对应的 D 编号、当前模块验收项、上次已审基线、本批文件差异、实际检查结果及剩余问题。不能只发送开发者的总结，也不能等模块写完才补审。

process_guardian 查看本批实际 diff 与必要的关联代码，逐项核对产出是否落实已批准要求，是否有越界、遗漏、擅自替换方案或降低验收标准。记录已审文件/基线、对应要求、证据、方案监督结论及未审部分。测试和业务疑点交 critic 或对应职能补证，总验收负责汇总；监督员不替他们签业务通过。

发现偏离时，主持暂停依赖该偏离的开发和提交，将问题交责任角色修正，再由同一监督员复核。已有授权覆盖的方案内修正直接落实；需要改目标、范围、业务策略或验收标准时，由总验收列出选项、影响和推荐交用户决定。其他不依赖该问题的已授权工作可以继续。

阶段完成时核对逐批检查是否覆盖全部产出，并收齐本职及总验收意见；提交前冻结文件，由监督员核对最终完整差异和内容摘要。后续变化须补审受影响部分并重新核对摘要，历史阶段 PASS 不能自动沿用。公开结论至少包括“本批做了什么、依据哪条方案、是否偏离、如何处理、尚缺什么证据”。现有 Hook 不会自动唤起代理，这项逐批调度由主持落实；漏调度须明确披露，不能补写成当时已审。

监督员提示词：

> 先读根目录 AGENTS.md，再完整读取 docs/协作规则.md、docs/项目方案与决策记录.md、docs/优化与问题修复记录.md 和 quality/active-module.json；其他文件只按明确引用或 rg --files 已列路径读取，不猜译名称。检查当前模块的用户方向、范围、方案与审查流程落实。每收到一批代码产出，查看相对上次已审基线的实际 diff 和必要关联代码，逐项对应已批准决定与验收要求，标明已审范围、遗漏、越界、擅自替换方案或降低验收标准；不能只读总结或等到提交前。核对四职能各自的实际意见、独立总验收报告、证据归属、未决问题和用户决定；业务疑点应交对应职能补证，由总验收汇总，不能代签职能或总体业务结论。按 D024 核对实际错误是否详细记录或简记、重复及阻断问题是否升级 E，区分确认原因与推断，保留失败尝试和限制。尤其检查 D006 Web 先行、组件可替换、不把模拟当真实声音。输出角色署名、过程/方案审查的 PASS 或 NEEDS_CHANGES、位置、偏离的决定、修正要求、证据和限制；明确这一结论不替代业务验收。发现偏离后跟踪责任角色修正及实际复核，涉及新取舍须交总验收整理供用户决定。准备正式提交时报告实际审查内容的 digest，内容变化则旧结论失效。纯待决策报告可确认记录与分工合规，但不得签业务无问题或已修复。不要修改业务代码，不生成伪造证据。

审查记录格式：

```json
{
  "module": "M00",
  "reviewer": "Plan Guardian（真实代理身份）",
  "verdict": "PASS",
  "digest": "quality_gate.py digest 的输出",
  "evidence": ["实际执行的命令与结果、真实功能判断"],
  "findings": [],
  "limitations": ["不能代替人工武汉话与音色验收"]
}
```

摘要涵盖所有入库候选文件内容和执行位，排除审查记录本身，防止自引用；Git/CI 会拒绝代码变化后的旧审查。审查记录仍是协作证明，并非密码学签名或不可绕过的权限控制，维护者不可冒用角色填 PASS。实质性结论在团队讨论聊天逐条展示，用户介入后同步给所有参与角色。

同模块补充审查使用 `docs/reviews/<模块>-<小写名称>.json`（如 `M02-docs.json`），并更新 `quality/active-module.json` 的 `review` 指向。命名必须匹配当前模块，不能跳出 `docs/reviews/`。历史审核保留当时结论，当前 PASS 必须针对最新内容摘要。阶段发言可由主代理如实转录，不能把未运行或历史通过写成当前复验。
