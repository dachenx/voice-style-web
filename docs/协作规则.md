# 项目协作规则

## 先读与当前目标

开始工作先读 `docs/项目方案与决策记录.md`、`docs/优化与问题修复记录.md`、`quality/active-module.json` 和 `docs/团队协作与方案监督.md`。
最新用户决定优先于旧方案。当前有效方向：Web 先行、组件可替换、声音效果迭代验证；音色克隆不等于武汉话能力。

## 一次一个模块

1. 当前模块的范围、允许文件、验收命令在 `quality/active-module.json` 中。开工时公布目标与完成标准，触发方案监督员审查。
2. 不得把多个业务模块一起实现。模块内每完成一个有意义片段运行 `python3 scripts/quality_gate.py quick`；自动 Hook 尚未可信或环境不支持时必须手动运行。同时按 D018 将本批实际代码差异、对应方案/决定、检查结果和剩余项交固定方案监督员 process_guardian 核对，不能只在开工和最终提交时监督。未审查批次明确标记，不能把 quick 通过当作方案监督通过。
3. 模块完成后运行 `python3 scripts/quality_gate.py full --no-review`，补充真实功能演示/测试证据。测试适配器不得被描述为真实语音效果通过。
4. 产品、语音技术、架构、质疑/质量四个真实子代理分别审查自己的职能范围；另设真实、独立、只读的总验收代理，汇总全部成员意见，核对端到端交接与证据。按 D015 和团队名册，一职能只保留一个固定负责人，先查现有代理并复用，不再创建同职责的审查副本。未提交意见的角色必须标为“未审查”，不能默认为同意；开发进度不能代替该角色的业务判断。本文件明确授权为此使用子代理。
5. 由固定的真实、独立、只读 Plan Guardian（process_guardian）检查用户方向、当前范围、每批代码的方案落实和审查流程是否真实执行。监督员不替代各职能判断，总验收代理也不得伪造或代签成员意见。开工、阶段完成、提交前均执行这一分工；开发中有意义的实现、修复及测试改动也须逐批监督。已发现的方案偏离在修正复核前暂停其依赖开发和提交；既定方案内的修正交责任角色按已有授权落实，涉及新取舍则由总验收提供方案交用户决定。不涉及某职能时，该角色仍须说明不适用的理由。
6. 公开各角色与总验收代理的实质意见，允许用户随时介入。总验收发现问题时列出证据、解决选项、影响和推荐，交用户决定，再由对应职能落实；按用户新要求，不能把建议自动记成已批准决定。需要补证时只向对应职能追问。没有问题时出具逐环节报告，列出通过依据和验证边界。主持负责调度、记录和执行已授权事项，不代替成员或总验收签署。
7. 将真实监督审查意见记录到 `docs/reviews/<模块>.json`（同模块补充审查可用 `<模块>-<小写名称>.json`，保留历史记录），内容摘要须匹配当前文件。总验收报告须同时保留各角色本职结论、总体验收、待决策项和用户决定；改代码后相关职能复验，总验收检查影响，监督员重审。历史监督 PASS 不追认为历史全员业务通过。
8. 同步决策与优化记录；无新决策/无优化也明确写明。成员齐备、总验收问题获决策并按约定处理、监督审核及严格 full 均通过后，执行 commit、立即 push，核实远端 SHA 与 CI 成功，最后报告模块完整交付。纯审查的待决策报告可先交用户，不冒称功能修复或完整交付，未解决项不得被写成通过。
9. 每个模块完成后向用户交付结果、证据和下一模块范围，再结束本轮。用户说继续后进入下一模块；已批准方案内的实施细节不重复询问，新增业务取舍仍须交用户决定。

## Git 与记录

- 远端限定 `dachenx/voice-style-web`，用户已授权公开仓库。首次建立 main；以后分支使用 `codex/` 前缀，一个模块一次主交付提交，修复可以独立提交。
- 提交格式：`chore(M00): ...`、`feat(M01): ...`、`fix(M01): ...` 等，必须带当前模块编号。
- 禁止 `--no-verify`、强制推送、静默跳过失败测试或为通过检查删除有意义的断言。不能擅自修改 Hook 信任记录。
- 决策追加到同一份 `docs/项目方案与决策记录.md`：背景、证据/讨论、选项、决定、原因、影响、验收、取代关系。保留旧决定并注明被取代。
- 优化追加到 `docs/优化与问题修复记录.md`：问题、复现/基线、修复、验证、剩余限制。不得编造性能提升。
- 真实录音、声纹特征、模型、生成结果、数据库、`.env`、密钥不提交。仅在 `tests/fixtures/` 存放人工构造的无个人信息测试文本。
- 不上传聊天原始转录、私人本机路径、会话标识；公开文档使用必要的方案摘要。

## 每次错误的记录要求

- 所有实际发生的非预期错误均及时追加到同一份 `docs/优化与问题修复记录.md` 的 E 编号记录，包括产品缺陷、测试/构建失败、Hook/CI 阻断、工具/环境错误及监督员发现的缺陷。未修好先记“待处理”，不能等成功后只写最终结果。
- 每条记录写明发生阶段与日期（不详则注明）、现象与影响、复现或来源证据、原因（区分已确认与推断）、每次修复/诊断尝试及其结果、修改文件/方法、实际验证、当前状态及剩余限制。已有提交或 CI 链接可引用；不得编造时间、错误栈或验证结果。
- 同一原因再次出现，按顺序追加尝试；不同原因新建 E 编号。失败尝试在修好后仍保留。历史补录标明来源和证据缺口，不声称恢复了没有留存的全部细节。
- 刻意输入坏文件、权限故障注入等预期负面用例属于测试覆盖，只有结果不符合预期才记为事故。非阻断警告另列限制，不能假装已经修复。
- 优化摘要 O 编号保留；逐条错误 E 编号与相关 O、D 记录互相引用。方案及形成过程仍只放决策记录，不另建分散的错误日志文件。
- 监督员在阶段和提交前审查中对照本轮工具结果、测试与修改，检查已知错误是否漏记、原因是否过度断言、状态是否有验证支持。脚本仅检查规定文件等结构约束，不宣称能自动发现所有未记录错误。
- 公开记录不得包含真实音频、密码/令牌/设备授权码、私人本机路径、会话标识或原始二进制长日志。用必要的脱敏错误摘要与仓库相对路径。

## 文档命名与历史

项目正文使用中文文件名。`README.md` 保留 GitHub 首页导航，`AGENTS.md` 保留代理入口并强制读取本规则；二者不再重复维护正文。重命名须同步活跃文档链接、检查脚本和测试夹具。历史审查 JSON 保留当时事实，不为改名改写旧审核，当前配置指向新的真实补充审查。

## 必须保持的产品约束

- 普通话原稿→武汉话草稿→人工确认→短段试听→全文生成→局部返修与导出。
- 模型、语言转换、发音处理均通过能力接口接入；不支持的参数不得假装有效。
- 每个任务保存不可变输入快照；编辑不改变正在运行的任务。
- 旧音频保留；过时和失败独立表示；依模型上下文范围识别受影响段落。
- 首版单人、本地、单任务队列；不擅自加视频、多用户、收费、云端集群。
- 软件验收和声音验收分开。声音需用户/武汉话熟练者试听，不由静态检查代替。
