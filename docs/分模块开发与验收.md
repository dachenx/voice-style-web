## 每个模块的交付循环

按 D020，每个模块实现完成后必须经过所有固定成员的本职审查，再进行总验收、最终监督和交付。下列“阶段完成”的全员审查以模块为单位；开发中仍逐批方案监督、按影响范围交相关职能复核。成员意见未齐时明确标为待审查，不把实现或测试完成写成完整交付；不涉及也须由该成员提交具体理由。

1. 更新 `quality/active-module.json`：模块 ID、base_commit、允许路径、验收标准及命令。前一模块未交付时不切换。
2. 开工按风险与影响调度相关职能，监督员核对最新决定、范围与参与落实；模块完成收齐四职能再由独立总验收汇总交接。每个有意义的代码片段结束做 quick，同时按 D018 交固定 process_guardian 查看实际差异并逐项核对方案落实；阶段完成及提交前重复对应审查。方案偏离须跟踪修正复核，涉及新取舍按 D014 给方案与影响交用户决定，未审角色或批次不得默认为通过。
3. 更新两份记录：决策形成过程、优化摘要以及按影响分级的错误记录（含失败尝试和未解决项），准备已有演示/测试事实并明确待验证项，随后冻结候选文件。
4. 由唯一执行方串行运行 full --no-review，执行本模块功能验收命令及治理回归测试。测试超时或无命令均失败，不把未运行当通过。检查退出后据实补充结果，运行 quick/diff/digest 交独立监督员复核；文档补充仍须更新摘要，不把旧摘要用于新内容。严格 Git 门禁继续执行完整检查。
5. 收齐四职能及总验收的真实结论和用户决定；未决事项不能写成通过。监督员反馈记录为 `docs/reviews/Mxx.json`；同模块补充使用 `Mxx-<小写名称>.json`，保留历史审核（参见 [团队协作与方案监督](团队协作与方案监督.md)）。修改后相关职能复验、总验收检查影响，重新生成摘要并监督复审。
6. `git add` 明确文件；pre-commit 要求索引与工作区一致，避免测试到未提交的版本；提交说明带模块编号。
7. push 当前模块分支；pre-push 只允许推送当前 HEAD，复查代码与审查摘要。确认远端 SHA、CI，再报告模块完成。
8. 展示可用结果、未解决项、下一模块范围后结束本轮，等待用户继续。

## 检查分层

- quick：中文正文及标准入口是否存在、模块范围、禁止提交的素材/密钥、Python 语法、JSON 解析、冲突标记和末尾空白。无法替代编译器或功能测试。
- full：quick + 标准库治理回归测试 + active-module 中声明的功能命令 + 独立审查记录。当前已包含后端 lint/typecheck/行为测试、前端 lint/typecheck/build 和浏览器验收；新增功能仍须注册对应检查，不能把语法扫描当功能验收。
- Codex：PostToolUse 检测文件摘要变化后 quick；Stop 在有修改时要求 full，失败提醒并最多自动续行一次。它不自行 commit/push，不绕过权限，不启动嵌套 AI。
- Git：pre-commit 与 pre-push 的硬门槛；commit-msg 检查模块号。新 clone 必须运行安装脚本。
- CI：在 push/PR 上运行 full，使用 checkout 内容；红灯不能视为模块完成。尚未启用服务器分支保护，CI 本身不阻止一次 push。
- 职能与总验收：四职能各签本职判断，总验收汇总、检查交接及逐环节行为，列方案让用户决定；没有待决问题时报告通过依据。当前脚本不能代替这项真实参与。
- 方案监督员：由唯一 process_guardian 逐批核对代码差异与既定方案，跟踪偏离的修正复核；同时核对范围、角色参与、总验收报告和用户决定、实际错误及修复是否按 D024 详细 E 或简记、是否及时升级，给出方案/过程审查结论。主持主动触发，不以 quick/CI 绿色代替；不代替职能或总验收签署。

## 回滚与公开文件

应用缺陷用独立修复提交或 `git revert`，不强制改写已公开历史。数据库迁移和模型配置变更需备份及恢复说明。真实音频、模型和数据库放 data/、outputs/、models/ 等本地忽略目录；测试仅用合成素材。

新增外部服务费用、云端上传、重大范围变化需先记决策并让用户明确选择。普通模块实现和已授权 commit/push 不反复询问。
