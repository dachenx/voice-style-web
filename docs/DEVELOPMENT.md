## 每个模块的交付循环

1. 更新 `quality/active-module.json`：模块 ID、base_commit、允许路径、验收标准及命令。前一模块未交付时不切换。
2. 开工审查：监督员核对最新 DECISIONS 与范围。每个代码片段结束做 quick；阶段完成审查是否偏离。
3. full --no-review 执行本模块功能验收命令及治理回归测试。测试超时或无命令均失败，不把未运行当通过。
4. 更新两份记录，准备功能演示/测试事实。运行 digest，交给独立监督员检查内容与事实。
5. 监督员反馈记录为 `docs/reviews/Mxx.json`（参见 TEAM.md）。修改后必须重新生成摘要并再次审查。
6. `git add` 明确文件；pre-commit 要求索引与工作区一致，避免测试到未提交的版本；提交说明带模块编号。
7. push 当前模块分支；pre-push 只允许推送当前 HEAD，复查代码与审查摘要。确认远端 SHA、CI，再报告模块完成。
8. 展示可用结果、未解决项、下一模块范围后结束本轮，等待用户继续。

## 检查分层

- quick：模块范围、禁止提交的素材/密钥、Python 语法、JSON 解析、冲突标记和末尾空白。无法替代编译器或功能测试。
- full：quick + 标准库治理回归测试 + active-module 中声明的功能命令 + 独立审查记录。未来加入 TypeScript/FastAPI 时必须在该模块注册 lint/typecheck/build/行为测试，缺少相应命令不能把语法扫描当功能验收。
- Codex：PostToolUse 检测文件摘要变化后 quick；Stop 在有修改时要求 full，失败提醒并最多自动续行一次。它不自行 commit/push，不绕过权限，不启动嵌套 AI。
- Git：pre-commit 与 pre-push 的硬门槛；commit-msg 检查模块号。新 clone 必须运行安装脚本。
- CI：在 push/PR 上运行 full，使用 checkout 内容；红灯不能视为模块完成。尚未启用服务器分支保护，CI 本身不阻止一次 push。
- 方案监督员：评审需求符合性、接口、模拟与真实效果、测试是否覆盖关键行为，给出 PASS/NEEDS_CHANGES 和证据。

## 回滚与公开文件

应用缺陷用独立修复提交或 `git revert`，不强制改写已公开历史。数据库迁移和模型配置变更需备份及恢复说明。真实音频、模型和数据库放 data/、outputs/、models/ 等本地忽略目录；测试仅用合成素材。

新增外部服务费用、云端上传、重大范围变化需先记决策并让用户明确选择。普通模块实现和已授权 commit/push 不反复询问。
